LifeX Policy Assistant · Prompt Behavior

What changed this session, and why

Six fixes to how the assistant reasons and talks — tone, depth, ranking accuracy, and follow-up handling. Each one below caused a real, reproducible problem; each fix was tested against the live backend before being trusted, not assumed.

Scope: src/query.py Test bed: 14-question quick-regression set Net result: 51/56 → 55/56 (3.64 → 3.93 avg)
This covers the prompt-behavior iteration round only. Earlier work this project — the gpt-5 model choice, the reasoning-effort tuning, the 11 chunk-content fixes, and the automated-extraction pipeline that was built and then shelved — is documented separately in Week4_Technical_Documentation.md.
Ranking accuracy

Fan-out questions weren't checking their own numbers before ranking

The problem

Asked "which lender is cheapest for a $200k primary asset?", the model's own answer listed Flexi at 7.30% — then, two sentences later, crowned Westpac "cheapest" at 8.17%. A higher number labelled as the lowest, in the same response.

Why it happened

When no lender is named, retrieval fans out across all 7 lenders (up to ~140 chunks), and that path deliberately runs at a cheaper reasoning setting (minimal) to avoid a 20–56 second latency blowout found earlier this project. That setting was calibrated for plain yes/no eligibility scans — it was never re-checked against questions that need an actual numeric comparison across the panel before answering.

The fix

A small classifier call (_classify_fanout_effort, same gpt-4o-mini pattern already used for follow-up resolution) decides per fan-out question whether it needs genuine ranking — bumping just those to the higher effort — rather than reverting every fan-out question to the slow setting.

Does answering this require comparing a number across lenders
and picking the best/cheapest/highest? Or is it a yes/no scan?
→ "low" effort if ranking, "minimal" if not

Validated

9/9 correct on a mixed test set, including a phrasing with no literal ranking word at all ("who's the better deal?") — a keyword list would have missed it, which is exactly why this used the same small-LLM-call pattern instead of pattern matching.

Tone

Panel answers read like a compliance form, not a broker

The problem

Every "which lenders can do X" answer forced one line per lender — "ANGLE — Yes-with-conditions: ..." — a format originally built to stop the model silently skipping lenders, but one that never reads like a person talking.

The fix

Rewrote the output-format instruction to group by verdict instead of by lender line — "X, Y and Z can do this; A and B can't" — while keeping the separate, untouched instruction that forces the model to check every lender internally before writing anything. Formatting and completeness turned out to be two different instructions doing two different jobs; only the formatting one needed to change.

Before

"ANGLE — Yes-with-conditions: finances heavy trucks/prime movers; company/trust only (no sole traders), 5+ yrs ABN & GST, 600+ score, property-backed; prime movers start from 9.39% and carry a 1% loading..."

After

"Short answer: Angle, CFAL, Flexi, Metro, Resimac and Westpac can all do trucks over 5.5 tonnes. BFS can't."

Validated

Ran 3 fan-out questions through both the old and new formatting side by side — every lender still got named in every run, zero silent drops, confirming the completeness guarantee survived the rewording.

Regression caught mid-fix

The verdict-grouping fix still let detail creep back in

The problem

Even grouped by verdict, a real question ("trucks over 5.5 tonnes") still came back with a dense clause per lender — ABN years, credit scores, loadings, age limits, stacked six times over. Technically grouped, still not how a broker talks.

The fix

Tightened the default depth: for a plain yes/no scan, naming who's in each group is the answer. Routine eligibility mechanics only get added back for a genuine hard exclusion worth knowing by name, or when a number is literally the thing being compared or ranked — not as a rundown of how each lender qualifies someone.

Still too much

"Angle — yes (includes prime movers; company/trust only, 5+ yrs ABN & GST, 600+ score, property-backed; prime movers start from 9.39% and carry a 1% loading; max EOT age 20yrs...)"

Tightened

"Angle — yes (includes prime movers; company/trust only, not sole traders)."

A second regression this caused, and the fix for that too

Cutting "extra depth" this aggressively also cut a genuinely necessary fact: a comparison question about Angle vs Resimac's primary-asset age used to correctly flag that their secondary/tertiary caps diverge (15/10 years vs 10/5) — exactly the failure mode that question is designed to catch. The tightened instruction quietly dropped that note along with the noise.

Fixed by carving out an explicit, non-negotiable exception: if a broker names one attribute and the same excerpt shows a closely-related figure that actually differs between the lenders being compared, that one line stays — it's a fact the question was testing for, not padding.

Validated

Re-ran the full 14-question set after each tightening pass. The divergence note held on retest; every other answer stayed short.

Behavior

The model answered questions it should have asked about first

The problem

Asked "what should I quote for the best commercial rate on a motor vehicle?" — genuinely unanswerable without knowing dealer vs private, new vs used, EV or not — the model still committed to a number, hedged with "if X then Y" branches covering every possibility instead of just asking.

The fix

Added an explicit decision rule: if the question already gives enough to reach a specific, defensible answer (an asset type, an amount, a borrower profile), answer it directly — more detail could theoretically sharpen almost anything, and that alone is never a reason to ask instead of answer. Only when a question gives close to nothing to work with does the direct answer become a short, natural clarifying question instead.

"Quick one: is it a dealer-sale car/light commercial under 5 years old, and is it an EV?"

Regression caught immediately

The first version of this rule was too eager — it made a perfectly answerable ranking question ("$200k primary asset, new, dealer, established company") ask for clarification too, inventing an unasked-about vehicle-weight distinction as the excuse. Tightened the test from "could this be refined further" (almost anything can) to "does this already give enough to answer" (most things do).

Validated

Genuinely ambiguous questions ask; a single missing, defaultable detail (e.g. dealer/private unspecified) gets answered with the assumption named in passing, not a question; a fully-specified calculation still just answers.

Cross-lender contamination

A single-lender question couldn't see the fact that would have saved it

The problem

Asked "CFAL's headline rate is 7.75%, right?" the model correctly refused to confirm the number — but had no way to say whose rate 7.75% actually is (Westpac's), because a CFAL-only question only ever retrieves CFAL's own chunks.

The fix

A prompt block already existed with exactly this fact ("CFAL shares DriveXpress with Westpac, but not its rate") — but it was scoped to multi-lender questions only, to avoid an earlier, confirmed problem where unconditional extra facts measurably hurt single-lender arithmetic questions. Added a minimal, CFAL-specific version of the same fact to the single-lender path, since CFAL doesn't have its own rates to calculate anyway — no arithmetic-question noise risk.

Validated

Confirmed the fix fires only when CFAL is the sole detected lender (checked a second CFAL-only question in the test set to confirm zero unwanted noise there), and that the model now names Westpac by name as the likely source of the confusion.

Contradiction-detection failure mode → 3/4 → 4/4
Root cause was one layer deeper than expected

A follow-up question silently switched into the wrong mode

The problem

Asked as a fresh question, "trucks over 5.5 tonnes" now answered cleanly. Asked as a follow-up — "what about over 4.4 tonnes?" right after — the old wall-of-detail answer came straight back, as if none of the day's fixes existed.

Why it happened

Follow-ups run through a completely separate code path: a small resolver call rewrites the message and decides whether it's a request for more detail on the same question, which deliberately switches off every brevity instruction (that mode exists on purpose, for when a broker genuinely says "tell me more"). Checked directly: the resolver correctly rewrote "4.4 tonnes" into a brand-new question — but also incorrectly flagged it as a "more detail" request, which is what pulled in the untouched, deliberately verbose branch.

standalone_question: "which lenders finance trucks over 4.4 tonnes?"   ← correct, new question
wants_more_detail:   True                                               ← wrong

The fix

Added a consistency rule to the resolver: "more detail" can only be true when the rewritten question is the same question restated. If any concrete detail changed — a different threshold, lender, asset, term — it's a new question at normal depth, no matter how the message is phrased ("what about...", "and...").

Validated

Tested 5 follow-up variations, not just the one reported: a different tonnage, a different asset (buses), a different age (used), a genuine "give me more detail" request, and one legitimately ambiguous case (asking to go deeper on "eligibility" for the unchanged scenario) — every one classified correctly, including the ambiguous one reasonably staying in detailed mode since nothing concrete actually changed.

Every fix above was tested against the live backend (real API calls, not assumptions) before being considered done, and re-verified against the full 14-question set after each subsequent change to catch regressions between fixes — two of which were caught and corrected mid-session (entries 3 and 4).
