LifeX Policy Assistant — Technical Documentation

How the retrieval-augmented lending-policy assistant is built: every module, why it's shaped the way it is, and the evidence behind each model choice.

System architecture

Five moving parts: a hand-curated (and now partly automated) knowledge base, a vector store, a retrieval + prompting pipeline, a FastAPI layer, and a self-correcting answer library sitting on top.

Two more subsystems attach to that spine:

  • Answer library (answer_library.py) — a persisted, embedding-matched store of human-reviewed and chat-corrected answers that gets checked before the LLM runs, and is kept in sync with chunk edits automatically.
  • Automated chunk-drafting pipeline (scripts/draft_chunks.py + table_geometry.py, wired into the API as /chunks/draft and /chunks/promote) — upload a lender PDF, get chunks drafted by a vision model grounded in deterministic table geometry, review the diff, approve some or all of it.
Design principle that shows up everywhere in this codebase: nothing auto-promotes into the live knowledge base without an explicit human (or, for in-chat corrections, the broker themselves) approval step. Chunk drafts land in data/chunks_draft/, never data/chunks/, until /chunks/promote is called. The one deliberate exception is chat corrections (see answer_library.py), which go live immediately by explicit product decision.

Chunk schema

Every fact the assistant can cite lives in data/chunks/*.md — one markdown file per lender (some split across "_v2" files from earlier corrections), each containing several chunks separated by a line containing only ---.

## chunk_id: bfs_customer_tiers
**source:** bfs
**topic:** customer_tiers
**intent:** ELIGIBILITY
**lenders:** BFS
**borrower_profile:** CONSUMER, COMMERCIAL, ...
**asset_class:** MV_NEW, MV_USED, LCV, ...
**doc_type:** ALL
**loan_size_band:** ALL
**answerable_questions:** Which BFS tier does my Experian score qualify for?
**confidence:** high
**last_verified:** 2026-07-29
**trigger_words:** customer tier, Ultra Prime, Tier 1, ...

**Content:**

BFS uses a two-group system (PRIME and PLUS) based on Experian CCR score...

src/ingest.py::parse_chunk_file() is the one place that understands this format — it validates lenders against VALID_LENDERS and intent against VALID_INTENTS at ingest time (a typo'd value doesn't error, it just silently makes that chunk unfindable by lender/intent-scoped search), and builds the metadata dict every retrieval filter runs against.

The answerable_questions and trigger_words fields aren't just documentation — they get prepended to the chunk's text before embedding (enriched_text in parse_chunk_file), so the embedding model learns to associate broker phrasing with the right chunk even when the chunk's own prose doesn't use those words.

src/config.py

Single source of truth for every model, path, and tuning constant. Every value below has a comment explaining why it's set the way it is — that history is as important as the value itself.

Why the embedding threshold is so high: a wrong cached/corrected answer served with confidence is a worse failure than a missed cache hit. The 0.90–0.96 similarity band was found to conflate genuine paraphrases with detail-changing near-duplicates for this domain's short, structurally similar questions — this trades recall for precision on purpose.

src/ingest.py

Turns data/chunks/*.md into embedded, queryable vectors in ChromaDB. Pure and deterministic — no LLM calls, no network dependency beyond downloading the embedding model once.

  • parse_chunk_file(filepath, warnings=None)Splits one file on \n---\n, extracts every **field:**, validates lender/intent against the known-good sets, and returns a list of LlamaIndex Document objects with id_=chunk_id. Populates warnings instead of raising — a malformed chunk gets flagged loudly rather than silently vanishing.
  • get_all_chunk_blocks()Flat {chunk_id: raw_markdown_block} across every chunk file — the exact original text, not the embedding-ready enriched version. Added for the answer library's staleness snapshots (see answer_library.py).
  • ingest_chunks()The full rebuild: parses every file, checks for duplicate chunk_ids across files (a real failure mode — ChromaDB just lets the second one silently overwrite the first), deletes and recreates the lifex_policies collection, embeds everything through a SentenceSplitter safety net, and prints a verification sample. Run via python -m src.ingest after any manual chunk edit, or automatically inside /chunks/promote.
A subtlety that matters elsewhere in the codebase: ChromaDB's own primary IDs are auto-generated per-node UUIDs from the SentenceSplitter transformation, not the chunk_id — chunk_id only survives as a metadata field. Looking a chunk up by its human-readable ID means filtering on where={"chunk_id": ...}, never collection.get(ids=[chunk_id]). This tripped up an early version of the answer-library source lookup in api.py (caught and fixed during testing — see that section).

src/query.py

The actual RAG pipeline. Everything downstream of "a broker typed a question" happens here: understanding what's being asked, deciding what to retrieve, building the prompt, and calling the answering model.

Lender detection

detect_lenders(question) returns every lender a question names, not just the first match — a two-tier keyword system (canonical name, then product/brand variants like "flexicommercial" or "metroeco"), unioned across lenders rather than short-circuiting on the first hit. A single-typo fuzzy fallback (Levenshtein distance ≤ 1) only kicks in when nothing matches at all, and is deliberately skipped for short codes like BFS/CFAL where a 1-edit match collides with ordinary words.

Bug this replaced: an earlier version returned as soon as any lender matched tier 1, which meant naming one lender by its canonical name silently suppressed a second lender mentioned only by product name. Confirmed via the 111-question eval — "Cross-lender comparison (2)" was the worst-scoring category specifically because of this.

Retrieval strategy

retrieve_nodes(question, lenders, log) retrieves every chunk for each relevant lender (up to ALL_LENDER_CHUNKS_K = 20 per lender — comfortably above any single lender's real chunk count of 8–10), letting embedding scores decide only the display order, never whether a chunk is included at all.

This replaced an earlier union/rerank/fan-out setup (including a cross-encoder reranker) built around a tight top-K cutoff. Its failure mode: a correct chunk ranked one place past the cutoff simply never reached the model — unrecoverable no matter how good the prompt was. Since each lender's whole chunk pool costs only ~5–6k tokens, including everything makes a retrieval miss for a scoped lender structurally impossible, and made the reranker (load time, ~1GB RAM, its own known demote-a-correct-chunk bug) unnecessary.

Prompt construction & guardrails

query_policies(question, verbose, history) is the orchestrator. In order:

  1. Resolves conversational follow-ups into a standalone question (_resolve_followup).
  2. Detects lenders, retrieves nodes.
  3. Builds context — a flat list for a single lender, or grouped under per-lender headings for multiple (a flat mixed list measurably caused the model to skip lenders when enumerating a panel-wide answer).
  4. Runs the profile-threshold check (_check_profile_threshold) and injects a note if relevant.
  5. Assembles the full prompt: verdict-first/brevity instructions, a lender enumeration checklist (only for multi-lender questions), known cross-lender pitfalls, conversation history, and the retrieved excerpts.
  6. Picks reasoning effort (REASONING_EFFORT if a lender is named, else a per-question classifier — see reasoning-effort tuning) and calls the answering model.

The prompt itself encodes a long list of hard-won, specific rules rather than generic instructions — e.g. "work the calculation breakdown before stating a headline number," "a hard exclusion can't be satisfied by a bigger deposit," "don't apply lender A's category rule to lender B just because the names are similar." Every one of these traces back to a confirmed wrong-answer bug in this project's own testing history; none are hypothetical.

Narrow LLM helpers

A recurring pattern in this file: rather than growing one giant prompt to handle every edge case, narrow, single-purpose classifier calls (all on RESOLVER_MODEL, cheap and fast) handle one well-defined judgment each.

  • _resolve_followup(question, history)Rewrites a follow-up ("what about westpac?", "give me more detail") into a standalone question, and flags whether the broker wants elaboration on the same answer (which turns brevity instructions off for that one turn) vs. a genuinely new question.
  • _classify_fanout_effort(question)For no-lender-detected questions, decides whether this specific one needs real cross-lender ranking (higher reasoning effort) or is a plain yes/no eligibility scan (cheapest tier). Built after finding that a blanket cheap tier missed constraint checks on genuine ranking questions.
  • _check_profile_threshold(question, context)General-purpose replacement for one-off "check field X against threshold Y" prompt bullets — looks for any customer-profile threshold table (ABN age, credit score, deposit...) and whether the question's wording places the customer against it.
  • detect_and_apply_correction(question, history)Detects whether a broker's message in chat is correcting the previous answer (not a new question, not "are you sure?" skepticism with no stated fact) — see answer_library.py for the full story and the fabrication bug this had to be re-engineered around.
  • refresh_answer_with_new_chunk(question, current_answer, old_chunk_text, new_chunk_text)Given a saved answer and its chunk's old/new content, decides: unaffected, needs a specific factual update, or too ambiguous to auto-apply. Powers the answer library's self-healing.

All narrow helpers share _chat_completion(model, prompt, max_output_tokens, json_mode, reasoning_effort) — the one place that knows the GPT-5 family's different calling convention (max_completion_tokens/reasoning_effort/verbosity vs. max_tokens/temperature), retries rate limits with the server-suggested backoff, and retries once (with a doubled token cap) if a GPT-5 model burns its entire budget on internal reasoning and returns an empty visible answer.

src/api.py

FastAPI layer. Thin where possible — most real logic lives in query.py/answer_library.py/scripts/draft_chunks.py — but owns request/response shapes, the promotion workflow's file-merge logic, and orchestrating the pieces together.

EndpointPurpose
POST /queryMain entry point. Checks (in order): is this a chat correction? → is there a matching answer-library entry? → is there a query-cache hit (disabled)? → run the full pipeline.
GET /healthStatus + live chunk count, for the frontend's connectivity check.
POST /answer-library/saveSame contract the frontend's Review tab already called — now additionally embeds the question and snapshots chunk content for staleness tracking.
POST /answer-library/refreshManually re-check every saved answer against current chunk content — for the "edited chunks by hand, didn't go through /chunks/promote" path.
POST /chunks/draftUpload a PDF + lender code → auto-drafted chunk markdown, diffed against the current live version. Never touches data/chunks/.
POST /chunks/promoteApprove some or all drafted chunk_ids → upserts into the lender's live file, re-ingests, reloads the live index, and cascades an answer-library staleness check scoped to exactly the chunks that changed.

The promotion merge (_split_raw_chunks / _render_chunk_file)

Promotion is an upsert by chunk_id, not a file overwrite — it parses both the draft and the live file into {chunk_id: raw_block} maps, replaces or appends only the selected chunk_ids, and re-renders the file. Untouched chunks in that file are preserved byte-for-byte. The merged result is validated (parse_chunk_file) against a temp file before it ever overwrites the live one — a bad promotion aborts with nothing changed, rather than leaving a broken production chunk file.

Why reload_index() exists

query.py builds its Chroma collection/index once at process start. ingest_chunks() deletes and recreates that collection through its own separate client — so without an explicit reload, the already-running process's in-memory objects would keep referencing a now-deleted collection, and every /query call after a promotion would break or silently serve stale data. reload_index() (in query.py) re-points every module-level global at the freshly rebuilt collection; /chunks/promote calls it immediately after re-ingesting.

src/answer_library.py — self-correcting answers

Closes a real gap: the frontend's Review tab already let a reviewer edit and approve an AI answer, but approved answers were write-only — never read back, and never checked against later chunk edits.

The three jobs this module does

  • save_entry(question, answer, chunk_ids) — embeds the question and snapshots the exact current content of every chunk_id the answer depends on. That snapshot is the baseline for staleness detection.
  • find_best_match(question) — checked at the top of every /query call with no conversation history. Same conservative 0.97 similarity threshold as the query cache, but actually served, since these are human-reviewed (or broker-corrected) entries, not raw unverified LLM output. Entries flagged needs_review are never served automatically.
  • refresh_stale_entries(changed_chunk_ids=None) — compares snapshots against current chunk content. For anything changed, calls query.refresh_answer_with_new_chunk to decide: unaffected (just refresh the snapshot), needs a specific update (auto_updated), or too ambiguous to auto-apply (needs_review, and stops being served until a human clears it). changed_chunk_ids scopes this to exactly what /chunks/promote just changed; None checks everything (the manual-edit path via /answer-library/refresh).
Verified live: a saved answer citing "7.30%" was automatically rewritten to "7.15%" after that exact rate changed in its source chunk — and a separate, unrelated addition to the same chunk correctly left the saved answer untouched (the refresh check judged it "unaffected" rather than rewriting something that didn't need it).

Chat corrections — the harder half

A broker can correct the assistant directly in conversation ("no, that's wrong, the max term is actually 72 months") and it saves immediately — a deliberate product decision that chat corrections don't wait in the Review queue the way AI-generated answers do.

Getting the classifier (query.detect_and_apply_correction) reliable took three iterations:

VersionApproachResult
v1Plain true/false + corrected_answer, asked directlyCorrectly rejected "what about Metro instead?" — but classified "are you sure about that?" as a correction and fabricated a specific replacement number with no basis
v2Added explicit contrastive examples, including that exact skepticism caseStill fabricated on that case; newly misfired on a close variant ("that doesn't sound right, can you confirm?")
v3 (shipped)Structural fix: the model must first extract broker_stated_value — quoting the specific new fact directly from the broker's own message — before it's allowed to answer is_correction: true11/11 test cases pass, including both fabrication triggers

The lesson (consistent with this project's general experience): when a model reliably fails at making a judgment directly, forcing it to first produce a concrete, checkable artifact — a quote, a value, a structure — tends to suppress the failure in a way that more prompt wording alone doesn't.

scripts/draft_chunks.py

Automated chunk drafting: render a lender's PDF pages to images, hand them to a vision-capable model alongside deterministic ground truth, and get back chunk markdown in the exact schema — instead of a human retyping tables by hand.

  • _build_content_parts(lender_code, pdf_files)For every page: renders a 2.5x-scale PNG, computes table_geometry.describe_tables_on_page(), and includes the exact digital text layer (page.get_text()) — three independent views of the same page handed to the model together.
  • draft_chunks_from_pdfs(lender_code, pdf_files, model, reasoning_effort)Core entry point, decoupled from disk paths — takes raw PDF bytes, so it works both for the CLI's pre-registered on-disk PDFs and for an arbitrary file uploaded through /chunks/draft.

The system prompt encodes the exact failure modes this pipeline exists to prevent — most importantly rule 9: whenever a DETERMINISTIC TABLE STRUCTURE block appears (from table_geometry.py), it is ground truth, overriding the model's own visual read of merged cells wherever the two disagree.

Why this exists as a separate, deterministic layer rather than trusting the vision model alone: six different model/config combinations (gpt-5 at high and low reasoning effort, gpt-4o, a two-pass merged-cell recheck, and two newer model variants) were tried against a real BFS rate table with a merged cell spanning three rows. None reliably told "merged across 2 rows" apart from "merged across 3 rows" from pixels alone — including reproducing the exact dangerous original bug. PDF table borders are usually real vector line objects, not just visual style, so whether a divider exists between two rows in a specific column is something code can check exactly instead of something a vision model has to guess.

scripts/table_geometry.py

Deterministic table-structure extraction from a PDF page's actual vector line data. Public entry point: describe_tables_on_page(page, page_label) → str.

The technique: _extract_grid_lines() finds every thin filled rectangle on the page (PDF's usual way of drawing a ruled line) and separates them into horizontal/vertical candidates; _find_tables() unions nearby segments into distinct tables via a simple union-find over bounding boxes; then for each column, the code walks the row boundaries and merges any consecutive rows where that specific column's divider is missing — even though the table overall has a boundary there, evidenced by other columns having a divider at the same y-coordinate.

This was cross-validated two independent ways on the real BFS bug: divider-line absence across all three row boundaries in the merged column (vs. present in an adjacent, correctly-per-row column at the same boundaries), and separately via text-centering math — the ambiguous value's actual y-position matched a 3-row-span hypothesis to within 1.6pt, against 12pt/3.4pt for the 2-row/1-row alternatives, calibrated against a known-unambiguous reference value sitting only 0.02pt off-center.

Testing & evaluation infrastructure

Everything under tests/ runs against the live backend over HTTP (uvicorn src.api:app --port 8000 must be running first) — these are integration tests of the real pipeline, not unit tests of pure functions.

  • tests/test_queries.pyRuns the 41-question scenario bank (policy_question_bank.xlsx). No auto-scoring — a heuristic keyword/number-overlap scorer was tried early on and gave false confidence (scoring a wrong lender's answer as correct because it happened to share enough words with the reference).
  • tests/run_complex_questions.pyRuns the full 111-question adversarial stress bank (ComplexQuestions.xlsx) — cross-lender comparisons, multi-filter, contradiction detection, negative/trap constraints. Reserved for milestone checkpoints, not every small fix.
  • tests/run_quick_regression.pyA curated 14-question subset covering every complexity type, every lender, and every question that's previously caught a real regression — for verifying a fix without paying for the full 111-question suite.
  • tests/grade_complex_questions.pyLLM-judge grading against the CMAP 2026 four-point rubric (4 = completely right … 1 = completely wrong), using a model independent of the answerer so it isn't marking its own homework. Reference answer and documented failure mode are given verbatim so the grader has a fixed target, and the raw transcript is kept alongside scores specifically so a human can spot-check any grade.

Model selection — embedding model

BAAI/bge-base-en-v1.5 (109M params), swapped up from bge-small (33M).

bge-small's retrieval recall in the 0.90–0.96 similarity band was the root cause behind needing a cross-encoder reranker at all — the reranker can only re-score chunks bge-small's first pass already found, so a chunk missed entirely at that stage was unrecoverable. bge-base is the same BAAI family (drop-in via HuggingFaceEmbedding, no new network dependency, no API cost) and scores meaningfully higher on retrieval benchmarks. bge-large (335M) was considered and rejected given this machine's prior history of memory-pressure issues — base was the safer size increase.

Combined with the "retrieve everything per lender" strategy (see retrieval), the embedding model's job narrowed to ordering chunks rather than gatekeeping them — which meaningfully lowered the stakes of this choice, and made the reranker's removal safe.

Speed & cost analysis

gpt-5.5 sits in the same non-mini/non-pro pricing tier as gpt-5 (OpenAI's naming convention distinguishes -mini/-nano as cheaper and -pro as more expensive within a generation) — this project doesn't have programmatic access to exact per-token pricing for point releases this new, so the honest comparison is the one actually measured: real latency across real questions, run against the live pipeline.

Two things worth being precise about:

  • Latency is a reasonable proxy for compute cost here, not a proof of it. Prompt sizes are near-identical between the two models (same retrieval, same context-building code), so the gap is dominated by each model's own generation/reasoning time — which is what OpenAI's usage-based pricing actually meters. A ~34% average latency reduction is suggestive of a real cost reduction, not just a UX win, but this project has not pulled an OpenAI billing-dashboard reconciliation to confirm the exact dollar delta.
  • The fan-out reasoning-effort remap ("minimal" → "none") was cost-relevant on its own — see below — and was validated with the same head-to-head discipline rather than assumed.

Reasoning-effort tuning history

The GPT-5 family exposes a reasoning_effort dial, and this project's history with it is a useful case study in "benchmark before trusting a default."

REASONING_EFFORT: minimal → low (2026-07-25)

At "minimal", multi-step rate calculations had a reproducible bug: the model would state a headline number before actually working out the right table row, then correctly derive a different number in its own shown breakdown and never reconcile the two (e.g. answering "9.64% p.a." as the headline while the working two lines later computes "12.64% + 2.00% = 14.64%"). Verified 3/3 that "low" eliminates this. Latency cost was real (~2–3x slower, 2–3s → 6–8s) but judged worth it over silently wrong headline numbers.

FANOUT_REASONING_EFFORT: kept at "minimal" separately (same date)

Applying "low" uniformly cost far more than 2–3x for the no-lender-detected fan-out path specifically — retrieval there spans all 7 lenders (~140 chunks vs. ~8–20 for a single named lender), and "low" effort over that much context measured 20–56s per question. Since this question type (broad eligibility scans) is mostly yes/no verdicts rather than the numeric rate build-ups "low" was raised to fix, it was scoped back down to "minimal".

A later, narrower fix: per-question fan-out classification (2026-07-27)

A blanket "minimal" for fan-out turned out too low specifically for ranking questions ("which lender is cheapest") — A/B tested: at "low" effort the model correctly excluded a lender whose discount only applied at a shorter term than asked for; at "minimal" it didn't always. Rather than reintroduce "low" for every fan-out question (reinstating the latency blowout), _classify_fanout_effort() now decides per-question whether a fan-out needs the deeper tier or can stay cheap.

FANOUT_REASONING_EFFORT: minimal → none (2026-07-31, the gpt-5.5 switch)

gpt-5.5 doesn't support "minimal" at all. Rather than pick a replacement by assumption, both plausible mappings were re-benchmarked head-to-head across 6 genuine fan-out questions:

Engineering principles this codebase follows

Patterns that recur across every module above, worth stating explicitly since they're what to reach for on the next bug or feature.

  • Structural fixes over more prompting, once prompting has been tried and measured to fail. The chat-correction fabrication bug wasn't fixed by better wording — it was fixed by restructuring the output contract so the model must produce a checkable artifact (a quote) before it's allowed to reach a verdict. Same story with table_geometry.py: six model/prompt combinations couldn't reliably read a merged cell from pixels, so the fix was a deterministic code check instead.
  • Narrow, single-purpose LLM calls over one growing mega-prompt. Follow-up resolution, fan-out effort classification, profile-threshold checks, correction detection, and staleness refresh are each their own small, cheap, well-scoped call — rather than one instruction list in the main answering prompt trying to cover every case.
  • Never trust a fix from one test case. Every model swap, prompt change, and reasoning-effort tier in this document was validated across multiple varied cases (2–3 minimum, often more) before being adopted — including deliberately re-testing known failure modes, not just the case that originally motivated the change.
  • No auto-promotion into anything a broker sees, except where a human explicitly is the approver. Chunk drafts always land in a separate directory first; a promotion validates before it writes; an answer-library refresh that can't confidently resolve a staleness check flags for review rather than guessing.
  • Verify visually/directly before asserting a structural claim, especially about tables. Learned the hard way from an early, wrong "merged cell" correction to a BFS rate table that itself needed correcting — the fix that stuck was building a tool that checks the actual PDF vector geometry rather than trusting a visual read, human or model.
