LifeX Policy Assistant · Architecture

How the whole system works

A retrieval-augmented Q&A backend covering 7 lenders' lending policy, built from hand-curated markdown chunks, ChromaDB for retrieval, and GPT-5 for answering — with a chain of small, targeted decisions layered on top to get the answers to actually sound and behave like a broker.

02The chunks: what a policy fact looks like at rest

Every fact the assistant can ever cite lives in data/chunks/<lender>_chunks.md — plain markdown, one chunk per ## chunk_id: block, separated by ---. Nothing is auto-extracted from the source PDFs; every chunk is hand-authored and hand-verified against its source document. Each chunk carries a metadata header:

## chunk_id: angle_interest_rates
**lenders:** ANGLE
**intent:** PRICING
**borrower_profile:** ...
**asset_class:** ...
**answerable_questions:** ...
**trigger_words:** ...
**Content:**
<the actual policy text>

src/ingest.py::parse_chunk_file() is the strict contract every chunk must satisfy — it validates lenders against a fixed 7-value set and intent against an 11-value set (PRICING, ELIGIBILITY, FEES, EXCLUSIONS, etc.), and prints a warning (not a silent skip) for anything malformed: an empty content section, an unrecognized lender/intent tag, or a duplicate chunk_id that would silently overwrite an earlier one in ChromaDB. answerable_questions and trigger_words get prepended to the chunk's text before embedding specifically so the embedding model associates natural-language phrasings with the chunk, not just its literal policy wording.

03Retrieval: why every lender's whole pool, not a top-K search

detect_lenders(question) is the first and most load-bearing decision in the whole pipeline — it decides both which chunks get retrieved and how hard the model has to think about the answer. Matching runs in two tiers per lender (canonical name, then product/brand variants like flexicommercial or premiumplus), unioned across all 7 lenders rather than stopping at the first match — a single-tier, early-return version of this is what silently dropped FLEXI from comparison questions that named it only by product name, an actual bug found via the 111-question eval. A single-typo fuzzy fallback (edit distance 1, names ≥5 characters) only kicks in when nothing matches on either tier.

Once lenders are known, retrieve_nodes() pulls every chunk belonging to each detected lender (ALL_LENDER_CHUNKS_K = 20, comfortably above any lender's actual 8–10 chunks) rather than a similarity top-K cutoff. If no lender is named, it does the same for all 7. This replaced an earlier union/rerank pipeline (a cross-encoder reranker, a tighter top-K) that existed to squeeze the right handful of chunks out of a lender's pool under a tight cutoff — its failure mode was that a correct chunk ranked one place past the cutoff simply never reached the model, unrecoverable no matter how good the prompt was downstream. Since each lender only has a handful of chunks (~5–6k tokens total), including everything costs little and makes a retrieval miss for a scoped lender structurally impossible — embedding scores now only decide chunk order, never inclusion.

Single vs. multi-lender context shape: for one detected lender, chunks are handed to the model as a flat, relevance-ordered list. For anything scoped to more than one lender (a named comparison, or the full 7-lender fan-out), chunks are grouped under a === LENDER === heading per lender, and the prompt is given an explicit list of exactly which lenders are present — this concrete checklist is what stops the model quietly stopping after 3–5 of 7 lenders, which a generic "cover every lender" instruction on its own did not reliably prevent.

04Two small classifier calls that steer the big model

Two purpose-built gpt-4o-mini calls (kept deliberately separate from the answering model — see §5) make small upstream decisions that the main prompt then depends on. Both exist because keyword matching demonstrably missed real phrasings; understanding intent is what an LLM call is for here, not a brittle word list.

_resolve_followup(question, history) → (standalone_question, wants_more_detail)

Rewrites a conversational follow-up ("what about westpac?", "give me more detail") into a question that stands on its own — this rewrite is what then drives lender detection and retrieval, identically to a fresh question.

Also flags genuine "give me more detail on that" requests, which switch off every brevity instruction downstream for that one turn. A consistency rule added this session forces wants_more_detail = false whenever any concrete detail (lender, number, asset, term) changed between the previous question and the rewritten one — otherwise a topic change disguised as a follow-up ("what about over 4.4 tonnes?") was misread as "elaborate on the 5.5-tonne answer," reactivating the old, deliberately verbose mode by mistake.

_classify_fanout_effort(question) → "low" | "minimal"

Only runs when no lender was named. Decides whether the question needs genuine cross-lender ranking ("which lender is cheapest", "who's the better deal") — which gets bumped to the full REASONING_EFFORT — or is a plain yes/no eligibility scan, which stays at the cheaper FANOUT_REASONING_EFFORT.

Exists because a blanket "minimal" effort for every fan-out question caused real ranking mistakes (naming a lender's rate as cheapest without checking every constraint in the question actually still applied to it). Fails toward the higher, correct-but-slower effort on any classifier exception.

05The answering model and its calling convention

All OpenAI calls — answering, both classifiers above — go through one function, _chat_completion(), specifically because the GPT-5 family and older chat models use different parameters, and hardcoding one style at each call site is how a previous model swap broke silently.

ModelRoleWhy this one
gpt-5Answering (LLM_MODEL)Benchmarked head-to-head against gpt-4o-mini and gpt-5-mini on 5 known-ground-truth questions: gpt-4o-mini made factual errors on full-corpus context, gpt-5-mini was correct but slow and verbose, gpt-5 was correct on everything, fastest of the GPT-5 family tested, and the only one that reliably followed the brevity/verdict-first instructions.
gpt-4o-miniFollow-up resolver & fan-out classifier (RESOLVER_MODEL)GPT-5-family models ignore temperature, so the same follow-up could resolve to a differently-worded standalone question on every run — tolerable for the final answer, not for something that feeds lender detection. 4o-mini at temperature=0 is deterministic and was already proven at this exact job.

For GPT-5-family models specifically, _chat_completion sets max_completion_tokens (reasoning tokens count against this, so it's the visible cap plus 512 headroom), reasoning_effort, and verbosity="low" — the last of these is the actual mechanism that constrains answer length; prompt text about brevity alone was found not to be enough on its own. If a response comes back empty because the whole token budget went to internal reasoning, the cap is doubled and retried exactly once (never in an unbounded loop) rather than surfacing a blank answer.

REASONING_EFFORTlowAny question with a named lender. Raised from minimal after a reproducible bug: at minimal, multi-step rate calculations sometimes stated a headline number before the model had actually finished deriving it, and never reconciled the mismatch with its own shown working.

06Prompt assembly: what turns retrieval into an answer

query_policies() is the orchestrator. In order:

  • Resolve follow-ups via _resolve_followup if there's history, producing the standalone question everything below actually runs on.
  • Detect lenders on that standalone question, retrieve every chunk for each.
  • Build the context block — flat for one lender, grouped-by-lender-heading with an explicit checklist for several — and, for a single detected lender, decide whether it needs a targeted "known pitfall" injected (currently CFAL only, see below).
  • Assemble the prompt: role framing, the lead-with-the-answer instruction with its two exceptions (calculations show working before the total; genuinely unanswerable questions get a short clarifying question instead of a guess), the checklist/brevity block when multiple lenders are in play, a block of known cross-lender mixups (bureau differences, CFAL/Westpac rate conflation, exposure vs. transaction limits), and a set of "double-check these common mistakes" bullets that catch things like hard vs. soft exclusions and lender-A's rule leaking into lender-B's answer.
  • Pick the reasoning effort (fixed low if a lender was named, otherwise the fan-out classifier's call) and the output cap (2000 tokens if the broker asked for more detail, 1000 otherwise), then call _chat_completion.
CFAL single-lender pitfall: the cross-lender mixup block above is deliberately scoped to multi-lender questions only — unconditional extra bullets previously measured as hurting single-lender arithmetic questions with noise they didn't need. But that meant a CFAL-only question, which never retrieves Westpac's chunks, had no way to recognize a broker quoting Westpac's rate as if it were CFAL's. A CFAL-specific fact (CFAL has no public rate card at all; a quoted headline rate likely belongs to Westpac's shared DriveXpress channel) was added to the single-lender path only when the sole detected lender is CFAL exactly — CFAL has no rates of its own to build up arithmetically, so this doesn't carry the same noise risk.

07The API layer

src/api.py is a thin FastAPI wrapper: one POST /query endpoint taking a question and optional conversation history, returning the answer plus its source chunks (id, lender, intent, retrieval score) and timing. An optional embedding-similarity query cache exists (QUERY_CACHE_ENABLED) but is currently off — its similarity threshold (0.97) was calibrated against the old, smaller embedding model and never re-validated after the swap to bge-base, and an uncalibrated cache risks returning a wrong-but-confident stale answer, which is a worse failure in a competition setting than a missed cache hit. Follow-up questions never read from or write to this cache regardless, since a cached answer to a conversational follow-up would make no sense served back as a generic answer later. Errors from the query pipeline (OpenAI down after retries, a ChromaDB hiccup) are caught and returned as an explicit 503 rather than an unhandled exception, so the frontend can tell "the backend is up but this question failed" apart from "the backend isn't running."
